01

先看懂：它在哪里运行，谁管什么

建议第一期采用：微信原生小程序 + 腾讯云开发 CloudBase 云函数、文档型数据库、云存储 + 小程序内工作人员工作台。先服务一个俱乐部，数据预留俱乐部编号，后续再扩展。

现有 HTML 到哪一步了？

现有 HTML 是可操作的产品演示，数据保存在浏览器本地。它还没有真实微信登录、服务器或数据库，不能直接把这个 HTML 上传成正式小程序。本手册是接下来开发和上线的执行说明，未替公司开通账户、购买云服务或提交审核。

02

主理人照着做：注册企业小程序

使用原始拉力（北京）运动服务有限责任公司的最新有效营业执照注册。公司名称和经营状态需由实际执照及官方登记信息核对，企业查询截图不能代替。下列步骤是操作路径；账号后台会随主体、验证方式调整材料和菜单名称。

先放进资料文件夹

法定代表人配合、公司授权 / 公章法定代表人核验或非本人管理员的授权；按所选注册、认证及备案流程要求准备

本期实际服务说明、条件资质和备案负责人资料按下一节整理；先把普通活动、训练与多日穿越的服务边界写清

  1. 打开官方注册入口

    主理人打开 mp.weixin.qq.com → 立即注册 → 选择“小程序”；也可用 小程序注册直达页。不要把公众号、微信开放平台或测试号当作正式小程序账号。

  2. 登记邮箱并验证

    主理人填公司控制的邮箱，收取激活 / 验证邮件，按页面回填验证码。本次核对的注册页为邮件六位验证码。本人设置并保管密码、阅读及接受服务协议；开发者无需持有密码。

  3. 主体类型选“企业”

    主理人按营业执照填公司全称、统一社会信用代码等信息。填的是实际经营公司，不是俱乐部昵称，也不借用开发者个人主体。

  4. 绑定管理员并完成真实性核验

    主理人 / 法定代表人按页面提交管理员信息、本人扫码。采用后台对该主体开放的验证方式；可能涉及法定代表人核验、对公验证或微信认证。若管理员不是法定代表人，依提示准备授权。必须由有权人员完成。

  5. 进入后台，补齐基本资料

    主理人设置名称、简称、头像、介绍和客服信息。介绍建议写“俱乐部非铺装摩托车活动招募、报名与成员积分管理”，实际包含训练时如实说明。名称审核与注册完成不是同一个环节。

  6. 确定服务类目，提交对应材料

    开发者协助在设置中的服务类目管理中选择匹配真实内容的类目。参照下一节逐项核对训练和活动内容；涉及前置许可的，先落实材料。保存后台审核结果和补件清单。

  7. 判断是否办理微信认证

    主理人根据实际类目、名称和接口能力看后台要求。不能把认证、主体核验和小程序备案当成同一项。普通发布不能一概认定必须每年交300元；需要办理时，以该企业后台订单金额、材料与有效期为准。

  8. 获取 AppID，添加开发成员

    主理人在“开发 / 开发管理 → 开发设置”找到小程序 AppID，交给开发者。在“成员管理”添加开发者的微信，分配开发所需权限；提审、发布权限按实际职责授予。AppID 是项目标识，AppSecret 是敏感密钥，不能写进前端或 HTML。

  9. 办理小程序备案

    备案负责人开发者协助从后台备案入口按引导填主体与服务信息，上传要求的证件、授权及行业材料，负责人完成真人核验，处理短信。可与产品开发并行；完成所需备案后才安排公开运营。

完成本节的交付物：

正式小程序账号、公司控制的管理员、AppID、开发成员权限、基本资料、类目审核情况、备案状态。登记成册，只记录“谁保管 / 去哪里查看”，不把身份证、密码和密钥放进交接清单。

微信官方：账号申请与 AppID · 微信认证 · 备案办理指引。本手册未登录企业后台，不能预先保证核验方式或审核通过。

03

上线前置条件：类目、备案和隐私

不标价、不在线收费，可以省掉本期的支付进件；真实的有偿活动及训练仍需如实申报。

事项本期怎样做通过的凭据
微信服务类目报名功能核对“工具 → 预约/报名”；真实包含技能训练，核对“体育 → 体育培训”。最终按具体服务和后台审核覆盖所需类目，不能只以报名外壳覆盖全部业务。已选类目及材料在后台通过；不能把类目表无证件列理解成线下训练无需资质
训练经营边界主理人提供课程、教练、场地和收费服务清单，向属地交通运输 / 体育等主管部门核实是否适用机动车驾驶员培训备案等要求。已有驾照、非铺装场地不当然免除。真实业务归类核对记录；如需许可或备案先办理；若适用“教育服务 → 驾校培训”，按后台交驾驶员培训备案材料
多日活动边界食宿交通由参加者直接自行预订支付，公司不代订代收；仍按实际是否组织、招徕和提供旅游服务判断。出现旅行社业务时先落实相应许可与类目。行程与责任说明、属地业务核对记录；触发旅游经营时按要求补证
小程序备案公司主体、负责人、服务内容、服务名称及按指引要求的授权、核验和前置材料；手机号保持畅通，按当前短信时限及时确认。微信后台显示备案完成；备案不是版本审核。平台初审、管局审核和补正均要留时间
隐私与用户规则写明使用的数据、目的、保存期限、第三方服务、删除与撤回方式、客服；后台填写用户隐私保护指引，与实际代码保持一致。需要隐私授权的接口按微信机制获取同意。能查看条款、申请删除 / 注销、退出榜单；拒绝可选授权仍能浏览公开活动
能力申请基础身份使用微信云端身份，不默认强制索取手机号、头像、定位。第一期扫码签到可不取 GPS；后加定位、手机号快捷获取、地图等，再核对接口权限、隐私申报和可能费用。所用接口在真机可用且获所需授权，不依靠开发工具“忽略校验”运行

报名需知道的本人、车辆、驾驶资格等信息按活动需要核验；第一期优先线下查验、线上保存必要结论与有效期，避免默认上传整张身份证或驾驶证。积分门槛不能替代现场技能、装备、场地和风险判断。

隐私指引去哪里填：公众平台“账号设置 → 服务内容声明 → 用户隐私保护指引 → 去完善”。首次提审或新版本增加数据处理时，也要在“版本管理 → 提交代码审核”的信息页面核对该版本的隐私指引；提审被拦截时，在提审入口修正对应版本，不能只改现网版本。

域名备案要不要？

本方案使用原生 wx.cloud 调用云函数与云资源，第一期不建设独立网站和自有 HTTP API，可不为了这套架构单独购买域名或 VPS。小程序自身备案仍要办。未来增加国内管理网站、自有 API 域名或网页嵌入，再核对网站 ICP 备案、HTTPS、微信合法域名及各产品接入要求。

完整材料与属地核对入口见 主理人指南第03节。平台依据：微信服务类目与资质、小程序备案、用户隐私保护指引。

04

开发者照着做：开通腾讯云与环境

选择腾讯云开发后，数据库、函数和文件存储都围绕一个“环境”管理。测试环境与正式环境要分开，每个环境有自己的环境 ID、数据和计费资源。页面版本的“开发版 / 体验版 / 正式版”不会自动替你隔离数据库。

  1. 先查公司有没有现成云账号

    主理人公司已开通过腾讯云时，先核对账号所有权、实名主体和已有资源；没有则用公司控制的账号完成注册及企业实名认证。公司保管找回方式、账单与续费联系方式，开发者使用获授权的成员。

  2. 核对腾讯云与小程序的绑定

    管理员开发者在腾讯云主账号的账号信息 / 登录方式中核对“微信公众平台”关联。使用既有公司腾讯云账号时，先按官方流程绑定本小程序；不要在未核对账号归属时一路自动开通，导致资源落在另一个账号里。已有环境不随意解绑、销毁。

  3. 安装工具，导入正式 AppID

    开发者从 官方入口安装微信开发者工具，用已加入项目的微信扫码，创建原生 JS/TS 项目并填写真实 AppID。若要接入既有公司云账号，按账号 FAQ 先创建“不使用云服务”的项目，再从云开发入口接入已关联账号的环境；这不代表产品不能使用云开发。

  4. 开通云开发服务并建两个环境

    有权人员确认条款与费用开发者配置工具中点击“云开发”，按提示开通；或在已绑定账号的云控制台创建并按官方流程关联环境。命名建议 oradv-test、oradv-prod，名字仅作标签，实际记录系统分配的 EnvId。创建页核对中国大陆可用地域、本项目所需文档型数据库、云函数和存储支持；地域选项以当时订单为准。

  5. 记录归属和费用

    开发者交付“AppID → 云账号 → 测试 EnvId → 正式 EnvId → 地域 → 套餐 → 到期日”关系表。环境初始化后确认两个库互不混用，测试导入不写到正式库；分别核对套餐和免费期。

  6. 配置预算、账单和告警

    主理人开发者确认付费套餐、续费和余额通知联系人。为用量、错误率和费用设提醒，先不无上限放开按量消费；如果设为配额耗尽停服，要让主理人明白活动当天可能中断。预算告警不是自动封顶。

  7. 初始化连接并验证

    开发者小程序初始化时指定目标环境，云函数使用当前部署环境，避免写死另一个环境。先部署一个仅返回当前身份和服务状态的内部测试函数，在真机确认成功；不要把手机号或密钥写进日志。

报名状态与积分规则先定下来

申请：报名意向 → 需要时资格审核 / 满员候补 → 待联系确认 → 员工确认参加。

现场：确认参加 → 出发核验 → 结束核验 → 实际完成 / 安全退出 / 未完成。

积分：有效完成后结算；只报名、确认或签到不自动发完成积分。重复结算不得重复发放；纠错追加反向流水并写明原因。

线下：员工在线下说明真实费用、服务范围、退改和风险，双方确认后才登记参加。小程序取消申请不等于线下退款完成。

六类真机验收要做

  1. 身份与权限：普通成员、主理人、运营、领队分别测试，撤掉角色后立即失去相关服务权限。
  2. 名额：至少两个人同时抢最后一个名额，只能一人占位；重复点击与网络重试不重复报名。
  3. 资格：积分不足、资格过期、人工审核未过都不能确认参加；积分足够仍需满足技能与现场条件。
  4. 签到：过期码、转发截图、重复扫描、错误活动和人工补签都有明确处理；偏远无网时使用领队离线名单并在恢复网络后由有权人员补录留痕。
  5. 结算：完成、安全退出、取消、未到场的结果正确；重复结算、并发结算及更正都能核对流水与总分。
  6. 隐私和异常：拒绝可选授权、退出榜单、申请注销、服务断开、备份恢复、手机尺寸和 iOS / Android 关键流程。

线下名单是网络中断时的业务预案；小程序不能在完全离线时保证所有云端报名、名额和积分实时一致。恢复联网后统一核对，不由客户端单方面发分。

必须由服务端保证的四件事

  • 身份：从云函数的微信调用上下文取得可信 OpenID，不能信任前端提交“我是谁 / 我是管理员”。OpenID 与昵称、手机号不是一回事；基本登录不需要因此收集手机号。
  • 权限：敏感集合禁止前端直接读写，所有业务写入经云函数验证身份、所属俱乐部、角色、状态和字段。云函数具有服务端权限，数据库客户端安全规则不能替它做业务鉴权。
  • 并发：报名记录使用可去重标识，名额和报名在事务中处理。一次活动一个成员的一次发分使用固定业务标识；流水、汇总和报名结算状态一致更新，网络重试返回原结果。大批结算分成员事务执行，逐条记录成功 / 失败。
  • 索引：至少覆盖已发布活动排序、活动报名状态、个人报名、成员年度流水和排名筛选；正式发布前以真实查询检查索引，不能等用户打开页面才报缺少索引。

备份怎么落地

在正式环境控制台核对当前套餐实际提供的备份 / 回档能力、保留期与恢复入口，并截取配置交接。另安排定时导出或快照策略、异地 / 独立权限副本及保存期限；数据库、云存储文件、代码和环境配置分别覆盖，不把“有数据库备份”当作全站备份。

建议验收：每天形成可验证的数据恢复点；上线前及关键数据变更前备份；至少每月把一份备份恢复到测试环境或新的隔离集合，对比报名数、积分流水与汇总，再记录结果。按这套日备份设计，最坏仍可能损失最近一次备份后的数据；若要求更低损失，需单独提高备份频率和预算。

数据库安全规则与服务端权限 · 数据库事务 · 数据库备份与恢复。集合名称、事务方案与备份频率为项目设计建议，需在实现和所购套餐中验证。

上线分成两次部署：业务后端部署到腾讯云；小程序代码包上传到微信。点开发者工具的“上传”，不会自动把数据库、云函数和权限一起部署好。

  1. 锁定待发布版本

    开发者代码仓库标记 v1.0.0；保存本次变更、发布负责人、目标 AppID 与正式 EnvId。所有示例活动、模拟登录、浏览器本地发分逻辑替换为正式实现。

  2. 准备正式数据结构和权限

    开发者在 prod 建集合、索引、安全规则、文件访问规则；导入俱乐部资料和必要规则，不导入原型虚构成员。更新已有库前先备份；测试导入脚本检查目标环境并拒绝误操作正式库。

  3. 部署正式云函数

    开发者在开发者工具中确认当前云环境为正式 EnvId；对各云函数执行“上传并部署”，按项目需要选择云端安装依赖，部署所需触发器与配置。数据库初始化、索引和存储权限需另外确认。项目也可用官方 CLI 自动化，但发布清单相同。

  4. 做后端验收并初始化角色

    开发者确认身份、公开活动、权限拦截、并发报名、签到和结算正常，完成首位主理人授权；查看云日志无关键异常。不能只在本地模拟器通过。

  5. 生成正式配置的小程序包

    开发者前端明确初始化正式 EnvId；核对 AppID、页面路径、隐私相关配置、能力申请和所需域名。纯原生云调用无需为了本方案额外加自有 API 域名；有外部网络请求则逐项配置合法域名，按正式校验在真机测试。

  6. 真机预览并上传

    开发者工具中先“编译 → 预览”，有权限的微信扫码检查。通过后点右上角“上传”，填写版本号 1.0.0 和清晰备注，例如“首版：招募、报名意向、员工确认、签到、积分”。

  7. 公众平台设置体验版

    有管理权限的项目成员登录公众平台 → 版本管理 → 开发版本，找到对应版本，设置为体验版。在成员管理添加主理人和领队为体验成员，发体验码。体验成员资格与业务员工角色是两套权限，都需配置。

    主理人 / 领队开发者用受控验收活动走通申请、确认、取消、核验与结算。测试数据与真实公开榜单、年度奖励隔离，记录清理 / 保留规则。通过后确认版本、说明和云端服务对应一致。

提审、被退回、发布：分别怎么处理

  1. 提交前核对五项状态

    开发者主体真实性验证完成；名称 / 类目及所需认证条件满足；小程序备案完成；隐私申报和实际能力一致；正式云端服务稳定、普通用户能完整体验。不把“已开通账号”当作已完成上述事项。

  2. 在版本管理中提交审核

    有提审权限的成员在开发版本找到验收过的包 → 提交审核；按表单选择功能页、服务类目、描述和所需材料。说明入口、报名及员工确认的流程，特殊审核路径按后台要求提供测试说明或合法的测试安排。

  3. 让审核员能看到真实功能

    开发者提供有效招募内容和可操作路径，避免只有空列表、已结束活动或“请先找管理员开通”的死路；需要解释员工端时提供清晰路径和录屏等适用资料。审核期间保持后端可用，不能临时隐藏训练、收费属性或审核后再开启未申报业务。

  4. 收到退回就按具体原因修改

    主理人补材料开发者修代码 / 说明记录原文原因：主体 / 类目问题补真实资料；隐私问题修申报及授权流程；功能问题修复、真机回归后上传新版本再提交。不能承诺固定几天通过，补正和行业核对另计。

  5. 审核通过后手动发布

    发布负责人版本管理 → 审核版本 → 确认版本号和业务准备 → 发布。审核通过通知不等于已经公开发布。首版发布后下载正式小程序码，用非项目成员微信检查真实访问、报名与权限。

  6. 发布当天盯住首场活动

    主理人开发者核对云付费状态、活动内容、客服、名额、报名、通知与积分；观察函数失败、数据库异常和额度。当天留下技术联系人，运营同步准备离线名单与现场联系渠道。

出故障按什么顺序处理

  1. 先保护正在报名和活动现场：必要时暂停新的确认 / 积分结算，保留客服和现场联系，领队使用预先准备的必要名单记录人员状态。
  2. 查日志定位：区分小程序代码、云函数、数据库索引、配额、欠费或微信接口问题；记录影响时间和范围。
  3. 恢复服务：代码问题按适用流程回退小程序版本或重新部署云函数；数据问题先在隔离目标恢复并核对，再决定正式修复。
  4. 业务对账：核对故障期间的报名、名额、签到、完成与积分，处理重试和遗漏，敏感更正留痕。
小程序版本回退，不会连同数据库一起回退。

云函数部署和数据变更也有各自的版本及恢复步骤。新后端要兼容仍在使用的旧前端；不要把重要字段直接删掉再发布。每次涉及数据结构和积分规则的修改，要有迁移与恢复方案。

  • 主理人 / 运营 / 领队工作台使用说明，角色授权与撤权流程，客服与隐私请求处理办法。
  • 一次可复现的发布记录和恢复演练记录；备份位置、保留期、故障联系人及维护工时 / 报价。
