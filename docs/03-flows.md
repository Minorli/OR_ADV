# 状态机、名额与异常

本章为建议的详细实现合同。待确认项见决策清单，不能从浏览器 demo 的按钮推导后台状态。

## 活动

draft 草稿 → published 招募 → closed 停止报名 → in_progress 进行中 → ended 待结算 → settled 已结算。开始前可从 published/closed 取消为 cancelled；开始后的安全终止作为 ended 并记录终止原因和各人结果，不直接抹掉签到数据。

提前关报名与到时间自动关闭结果一致。取消后停止报名和签到，保留通知记录。结算完成禁止普通编辑奖励规则；纠错走冲正。修改日期、地点风险、资格、积分等重要内容创建新版本并通知已申请者，是否要求重新确认由运营明确。

## 报名主流程

普通成员：pending_confirmation 待管理员确认 → confirmed 确认参加 → checked_in 已出发核验 → pending_settlement 已结束待核验 → completed 完成。创始成员满足必要条件后直接进入confirmed。旧pending_review状态继续兼容，必要资格核验仍独立进行。

waitlisted 候补；rejected 审核未通过；cancelled 取消；no_show 未到；safe_exit 安全退出。后四种不按正常完成直接发分。安全退出和活动终止的积分政策需主理人确认，默认没有完成奖励。

资格状态单独保存 reviewDecision，名额状态单独保存 seatState。不要用“已报名”一个字段同时表达资格、联系、缴费和参加。

## 准入和名额

提交申请时，服务端读取：活动仍可报名、未过截止时间、成长分达到门槛、必要技能资格是否有效、是否已有有效申请、是否有可用名额。员工批准时再次验证失效资格，现场再核验。

建议首版待审核/待确认即预留名额，候补不占位；这是 proposed 规则。member+activity 的报名文档 ID 固定，重复提交返回已有状态。取消后重报复用文档、增加 attempt/revision 并保留审计，不能产生两个有效名额。

活动文档维护 reservedSeats，申请与占位在一个事务中完成。不能先读剩余人数再分别写，不能靠前端缓存防超额。有效座位 held→released 只能一次；pending_review、pending_confirmation、confirmed 消耗名额；候补不消耗。活动进行后保留历史 reservedSeats，不因完成而重新开放报名。

初版不设自动超时释放，holdExpiresAt=null；若之后采用超时机制，必须同时定义时限、通知、恢复和并发处理，不能脚本偷偷释放已经确认的用户。

## 候补

候补按服务端申请序号排序；资格审核独立。释放名额后，事务选择最早仍有效的候补，重新检查成长分和资格。0.2a由运营主动提升最早仍有效候补，创始成员符合当前条件时直接confirmed，普通成员进入pending_confirmation；预留座位一次，更新站内状态，模板消息能力另按实际授权。没有订阅权限不影响状态正确。

候补提升和取消并发必须有版本条件。不能在获得有效名额和通过当前条件核对之前把候补标confirmed；符合条件的创始成员获席后可按已确认政策直接确认。到报名截止后默认停止自动提升，需运营明确延后并留痕。

## 核验与结算

出发核验由现场员工操作，或使用短期一次性凭据并由员工确认；不能用静态截图即完成。仅限 confirmed，核验员工有该活动权限。结束核验需要出发记录和领队结果。多日活动记录每天人员状况，最终一次完成结算；每日签到不重复发整场分。

活动结束后，领队逐人确认完成、退出、未到和异常，运营预览结算名单，服务端按发布时冻结规则逐人事务结算。大场次分批执行，有状态与失败清单，重试不重复。

## 必须覆盖的异常

取消和签到同时发生；最后一个名额被多人争抢；资格在报名后过期；活动改期；用户换手机仍同一 OpenID；领队换人；网络中断后重试；已完成用户要求更正；年度冻结后发现错误。每种需在验收记录体现，不靠“刷新看看”判断正确。

## 后续报名分流的最新依据

用户已补充创始／核心成员直接确认、普通成员线下缴费提示后由管理员确认的要求，详见 [产品设计4.1节](20-product-design.md#41-两类报名路径)。0.2a已在服务端实现两类路径、身份版本快照、重报与候补分流，并同步合同和回归测试；真实云端仍待验证。推荐展示的优先级不自动改变候补顺序。
